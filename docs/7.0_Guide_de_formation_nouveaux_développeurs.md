# 7. Guide de formation — Nouveaux développeurs

Point d'entrée pédagogique pour tout développeur rejoignant l'équipe de raccordement SSO.
Structuré en 7 modules progressifs, du contexte général jusqu'à la mise en pratique sur dépôt réel.

**Durée estimée totale :** ~2 jours (adaptable selon le profil et le projet d'affectation).

**Prérequis :** accès à l'espace Confluence du projet, compte GitLab opérationnel, accès au ticket Jira de l'application concernée.

---

**Ordre recommandé :** M1 → M2 ou M3 ou M4 (selon votre premier projet) → M5 → M6 → M7.
Les modules 2, 3 et 4 peuvent être abordés dans n'importe quel ordre après M1 ; commencez par le protocole du projet sur lequel vous intervenez.
M7 se fait sur un dépôt réel fourni par le formateur — commencez-le uniquement après avoir lu le guide correspondant à votre projet.

## Module 1 — Contexte & concepts (~3h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- situer la migration dans son contexte (pourquoi, qui, quels environnements) ;
- distinguer authentification et autorisation ;
- décoder la structure d'un JWT ;
- définir les concepts clés OIDC et SAML ;
- choisir le bon guide pour votre premier projet.

### Exercice

Décoder manuellement un JWT de test sur [https://jwt.io](https://jwt.io) et identifier : `iss`, `aud`, `sub`, `exp`, `email`.
Quel claim sert d'identifiant stable pour corréler un utilisateur en base de données ?

---

## Module 2 — OIDC Gestion managée — Guide 1.1 (~2h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- expliquer ce que fait le module Apache `mod_auth_openidc` à la place de l'application ;
- lire un claim dans les variables d'environnement (`OIDC_CLAIM_*` vs `REDIRECT_OIDC_CLAIM_*`) ;
- adapter le code dans les langages courants (PHP, Python, TypeScript) ;
- dérouler les phases A→F du tableau de suivi.

---

## Module 3 — OIDC Gestion privée — Guide 1.2 (~4h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- choisir entre flux avec et sans PKCE selon le type d'application ;
- implémenter les étapes du flux Authorization Code (§ 4.1 à § 4.8) ;
- valider un ID Token (signature, issuer, audience, nonce, expiration) ;
- identifier et corriger les pièges courants (`redirect_uri`, state/CSRF, secret exposé, scopes manquants).

---

## Module 4 — SAML Gestion privée — Guide 1.3 (~4h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- distinguer les deux chantiers SAML (contrat SP/IdP vs mapping applicatif) et ne pas les mélanger ;
- configurer une bibliothèque SAML avec les métadonnées IdP ;
- implémenter le callback ACS (réception Response, validation signature, extraction NameID/attributs, session) ;
- choisir et tester la stratégie de déconnexion (SLO ou locale).

---

## Module 5 — Processus & communication (~1h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- utiliser le bon template de mail à chaque étape clé ;
- tracer correctement dans Jira (mails, MR, dates de déploiement) ;
- identifier clairement ce qui est dans votre périmètre.

### Les templates de mail

| Template | Quand l'utiliser |
| --- | --- |
| **4.1 Prise en charge technique (gestion managée)** | Étape 13 du guide **1.1** : vous prenez en charge les modifications de code. |
| **4.2 Fin d'intervention technique (guide 1.1)** | Après la MR du guide **1.1**. |
| **4.3 Prise en charge technique (gestion privée)** | Étapes 10, 19, 27 du guide **1.2** / étapes 10, 22, 32 du guide **1.3**. |
| **4.4 Information utilisateurs** | Avant toute mise en production (guides **1.1**, **1.2**, **1.3**). |
| **4.5 Fin d'intervention technique (guides 1.2 / 1.3)** | Après la MR des guides **1.2** ou **1.3**. |

### Le PV de recette — votre rôle exact

- Vous **accompagnez** la recette SSO (connexion, déconnexion, affichage des claims).
- Vous **ne signez pas** le PV : c'est la responsabilité exclusive de l'équipe applicative.
- Le PV est **validé avec le CAM Eagles**.

### Périmètre de mission

> [!NOTE]
> **Dans votre scope** : transmission de la fiche de renseignement à l'IAM, injection des credentials reçus (client_id, client_secret, endpoints...) dans les variables d'environnement, adaptation du code applicatif, suivi des bascules, recette SSO.
>
> **Hors scope par défaut** : déploiement applicatif, provisionnement d'infrastructure.
>
> **Exception** : si l'équipe applicative est en défaillance DevOps, vous pouvez intervenir sur le déploiement (voir document **5. Guides de déploiement**).

---

## Module 6 — Déploiement (~1h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- identifier les deux modes de déploiement (manuel vs pipeline) ;
- savoir quand il vous revient d'intervenir sur le déploiement ;
- réaliser un déploiement manuel pas à pas (MyConsole Cloud, Console Web AWS, Docker Compose).

---

## Module 7 — Mode opératoire IA (variable)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- conduire une migration SSO de bout en bout sur un dépôt réel avec assistance IA ;
- produire un historique Git propre et une MR reviewable par un pair ;
- identifier des améliorations à remonter sur le dépôt **init-dev**.

Suivre le document **6. Mode opératoire — Migration SSO avec assistance IA** sur le dépôt fourni par le formateur.
