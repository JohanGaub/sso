# 1.3 Guide migration SAML - Gestion privée

En gestion privée SAML :

- Le CAM Eagles fournit la **fiche de renseignement** à l'équipe IAM avec les informations pour configurer Entra ID (EntityID du SP, URL ACS, URL SLO, bindings, attributs nécessaires).
- L'équipe IAM configure Entra ID (interface dédiée), ce qui génère les métadonnées IdP (SSO URL, certificat x509, endpoints SLO), puis les transmet via le CAM Eagles à l'équipe applicative.
- L'équipe applicative reçoit les métadonnées IdP.
- L'équipe applicative et/ou l'équipe de raccordement configurent l'application côté SP (bibliothèque SAML, métadonnées, bindings, certificats).
- L'équipe applicative adapte la lecture des **attributs** nécessaires au fonctionnement de l'application (NameID + attributs de l'Assertion).

> [!NOTE]
> **NB :** en gestion privée, l'application implémente le flux SAML (SP-initiated ou IdP-initiated — voir **§ 3. Prérequis**) ; les attributs se lisent dans l'**Assertion** (NameID + attributs) — voir **§ 4.6**, **§ 5. Attributs (Legacy → IdP)** et **§ 7. Exemples de code**. Deux chantiers distincts : **contrat SP/IdP** et **mapping applicatif** — lisez **§ 3. Prérequis** avant de commencer.

## 3. Prérequis : deux notions que tout le monde mélange

> **Décision flux (déclencheur) :** **SP-initiated** (recommandé — l'application initie l'authentification) sauf contrainte métier imposant **IdP-initiated**. Détail en **§ 4.4 Choisir le mode d'initiation**.

- **Contrat SP/IdP (ce que la fiche engage avec l'IAM)** — ce n'est **pas** du remplacement de clés dans le code. À valider tôt : **URL publique** réellement atteinte (y compris reverse-proxy), **ACS**, **EntityID**, **SLO** si concerné, **bindings** (Redirect/POST), mode **SP-initiated** vs **IdP-initiated**, **certificats** et **signature** (Response/Assertion).

  Si une ligne de ce bloc ne correspond pas à ce qui tourne vraiment en hors production (dev / recette), le SAML casse **avant** que votre nouveau mapping d'attributs ne serve à quoi que ce soit.

- **Mapping applicatif (ancien → nouveau)** — c'est bien le remplacement des anciennes clés/valeurs par ce que vous lisez dans l'**Assertion** (NameID + attributs). C'est surtout les **étapes 8** (tableau) et **15** (code) du **Suivi à réaliser**.

**L'étape 7** du tableau de suivi = une **passe courte** sur le **contrat SP/IdP** uniquement : la fiche dit la même chose que l'infra/l'appli va exposer ? Dans Jira : **lien ou référence** vers la fiche ; **mémo court seulement si écart** (pas de duplication de la fiche).

### 4.1 Configurer la bibliothèque SAML avec les métadonnées/certificats

Avec les métadonnées produites à l'étape **9** (métadonnées SP) et réceptionnées à l'étape **12** (métadonnées IdP) du **Suivi à réaliser**, configurez votre bibliothèque SAML :

- EntityID du SP et endpoint ACS (URL de callback).
- URL de SSO de l'IdP et certificat x509 de signature (issu des métadonnées IdP).
- Paramètres attendus côté SP (issuer/EntityID, et audience si applicable) + activation de la vérification de signature.
- Requête AuthnRequest côté SP : `Issuer` doit correspondre exactement à l'identifiant déclaré côté Entra ID, et `ID` doit être unique (et ne pas commencer par un chiffre) pour sécuriser le contrôle `InResponseTo`.

### 4.2 Définir le NameID

Le NameID est l'identifiant de l'utilisateur dans l'Assertion SAML.

- Formats de NameID supportés :
  - `urn:oasis:names:tc:SAML:1.1:nameid-format:unspecified`
  - `urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress`
  - `urn:oasis:names:tc:SAML:2.0:nameid-format:persistent`
  - `urn:oasis:names:tc:SAML:2.0:nameid-format:transient`

- Comportement Entra ID :
  - si l'AuthnRequest contient une `NameIDPolicy` avec un format demandé, Entra ID utilise ce format ;
  - si aucun format n'est demandé, Entra ID applique le format configuré côté application (par défaut : `unspecified`) ;
  - pour `transient`, si le SP le demande, Entra ID renvoie une valeur aléatoire unique à l'opération SSO (valeur temporaire, non réutilisable).

### 4.3 Vérifier la signature SAML

> [!WARNING]
> **À faire absolument :** activer la vérification de signature côté SP et refuser toute réponse non conforme.

Les tokens SAML renvoyés par Entra ID sont signés, mais **le périmètre exact de la signature est un paramètre de configuration** (réponse, assertion, ou les deux).
Dans la pratique, votre bibliothèque doit être capable de vérifier la signature au bon niveau : **Response** (élément `saml:Response`), **Assertion** (élément `saml:Assertion`), ou les deux, selon ce qui est configuré côté IdP.

- Côté IdP (Entra ID) :
  - Entra ID peut signer :
    - l'Assertion (option la plus courante / souvent par défaut),
    - ou la Response,
    - ou la Response **et** l'Assertion ;
  - le certificat public correspondant figure dans les métadonnées IdP.

- Côté SP (votre appli) :
  - la bibliothèque SAML (OneLogin, simplesamlphp, passport-saml, etc.) doit être configurée avec le certificat de l'IdP ;
  - la vérification de signature doit être activée : le SP doit refuser une Response/Assertion :
    - dont la signature est invalide,
    - ou qui n'est pas signée,
    - ou qui ne vient pas du certificat attendu.

> **À retenir :** ne jamais désactiver la vérification de signature en production pour contourner un incident.

#### Checklist de validation minimale (dev-first)

- Signature SAML : présente et valide (Response et/ou Assertion, selon config).
- Issuer : correspond à l'IdP attendu (éviter toute confusion d'environnement).
- Audience : correspond à l'identifiant attendu côté SP (EntityID / App ID URI selon configuration).
- Fenêtre de validité : `NotBefore` / `NotOnOrAfter` cohérents (horloge serveur à l'heure).
- Correlation : `InResponseTo` correspond à l'AuthnRequest envoyée (en SP-initiated).

### 4.4 Choisir le mode d'initiation (SP-initiated vs IdP-initiated)

- **SP-initiated SSO** (mode recommandé) :
  - l'utilisateur commence par accéder à l'appli (SP) ;
  - le SP génère une AuthnRequest et redirige le navigateur vers l'IdP (HTTP-Redirect) ;
  - après authentification, l'IdP renvoie une Response SAML signée vers l'ACS du SP (HTTP-POST).

- **IdP-initiated SSO** :
  - l'utilisateur clique sur la tuile de l'appli dans le portail Entra ID / My Apps, ou sur une URL IdP-initiée ;
  - l'IdP authentifie l'utilisateur (et applique les politiques de sécurité) ;
  - l'IdP envoie directement une Response SAML signée vers l'ACS de l'appli.

Ce mode est supporté par Entra ID mais n'est pas le scénario recommandé par défaut. L'appli doit simplement :

- exposer une URL ACS cohérente avec la configuration Entra ID ;
- accepter la Response SAML reçue, quel que soit le mode d'initiation.

### 4.5 Choisir le binding (HTTP-POST vs HTTP-Redirect)

Deux bindings SAML sont utilisés dans Entra ID :

- **HTTP-POST** (`urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST`) :
  - les messages SAML (notamment la Response contenant l'Assertion) sont transmis via un formulaire HTML encodé en Base64 et envoyés en POST vers l'ACS du SP.

- **HTTP-Redirect** (`urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect`) :
  - les messages SAML (ex. AuthnRequest) sont passés en paramètres d'URL et envoyés via une redirection HTTP.

Comportement attendu côté application (SP) :

- AuthnRequest → en pratique, envoyée en HTTP-Redirect (SP → IdP) ;
- Response SAML → en pratique, reçue en HTTP-POST (IdP → SP, vers l'ACS).

Ces bindings suivent le profil SAML 2.0 "Web Browser SSO" et constituent le mode de fonctionnement par défaut avec Entra ID.
Pour le **single logout** SAML avec Entra ID, le binding utilisé est HTTP-Redirect (GET), pas HTTP-POST.

### 4.6 Implémenter le callback ACS (Response + NameID/attributs + création de session)

Déclenchez votre logique d'authentification à l'URL ACS :

- Réception : récupérer la Response SAML soumise en POST.
- Validation : vérifier la signature au niveau configuré (Response et/ou Assertion), puis contrôler issuer, audience, fenêtre de validité, et correlation `InResponseTo` (doit correspondre à l'`ID` AuthnRequest émise côté SP en mode SP-initiated).
- Extraction : lire le NameID et les attributs depuis l'Assertion, puis appliquer le mapping de la section **Attributs (Legacy → IdP)**.
- Session : créer la session applicative (et stocker ce qui est nécessaire côté app), puis finaliser la redirection/retour.

### 4.7 Gérer la déconnexion (SAML SLO vs déconnexion locale)

> **À faire absolument :** choisir explicitement une stratégie de déconnexion (SLO ou locale) et la tester.

Deux cas sont possibles : mise en œuvre du SLO SAML, ou déconnexion locale (fallback).

#### Single Logout (SLO) SAML

- Le SLO permet de synchroniser la déconnexion entre IdP et SP :
  - une déconnexion initiée par l'utilisateur ou par une appli peut fermer les sessions SSO sur les autres applis fédérées via le même IdP.
- Dans Entra ID :
  - le SLO est pris en charge, mais nécessite une configuration explicite de la `LogoutURL` côté application Entra ID ;
  - le flux SLO Entra ID utilise le binding HTTP-Redirect (GET).
- Côté SP :
  - exposer un endpoint de déconnexion (`SingleLogoutService`) ;
  - accepter et traiter les messages `LogoutRequest` / `LogoutResponse`.

Si le SP ne supporte pas le SLO, prévoir un fallback : déconnexion locale (détruire la session applicative et rediriger vers une page d'atterrissage).

#### Déconnexion locale sans SLO

Il est possible de déconnecter un utilisateur d'une appli sans mettre en œuvre le SLO SAML.

- Cinématique recommandée avec Entra ID :
  - l'utilisateur clique sur "Déconnexion" dans l'appli ;
  - l'appli détruit la session locale (cookies, jetons, session serveur) ;
  - l'appli redirige l'utilisateur vers l'URL de déconnexion globale Entra ID ;
  - Entra ID termine la session SSO et affiche une page de confirmation ou redirige (optionnel) vers une URL définie.

- Points clés :
  - cette méthode ne synchronise pas la déconnexion avec les autres applis (contrairement au SLO) ;
  - elle est plus simple à mettre en œuvre ;
  - si une URL de retour est utilisée, elle doit être déclarée dans la configuration de l'appli dans Entra ID.

### 4.8 Tester et diagnostiquer

Objectif : valider que l'enchaînement 4.1 → 4.7 produit une connexion correcte et robuste.
Cette section décrit **les scénarios à exécuter**. La **Checklist rapide** sert de contrôle immédiat, et la **DoD** sert de validation finale avant livraison.
**Entrée attendue :** sections 4.1 à 4.7 implémentées et exécutables dans l'environnement de test.

**Cas à tester :**

- login OK (SP-initiated et/ou IdP-initiated selon votre scénario)
- login échoué : signature invalide / mauvais certificat, issuer inattendu, binding incorrect
- attributs manquants ou inattendus : NameID absent, attribut non mappé
- déconnexion : SLO si activé, sinon déconnexion locale (fallback)

**Checklist rapide** (ce que vérifier en priorité) :

- **§ 4.1** métadonnées/certificats : bon ACS/EntityID + bon certificat de signature
- **§ 4.3** signature : niveau Response/Assertion conforme à la config IdP
- **§ 4.4** mode d'initiation : le SP accepte bien le type de réponse attendu
- **§ 4.5** binding : Response reçue en POST sur l'ACS attendu
- **§ 4.6** callback : extraction correcte et mapping appliqué
- **§ 4.7** déconnexion : stratégie validée (SLO si activé, sinon locale)

En cas de doute, activez des logs détaillés en hors production (dev / recette) (sans données sensibles), et gardez des messages clairs en production (attribut manquant/invalide, signature refusée, etc.).
Si le blocage concerne la validation de signature, revenez d'abord à **§ 4.3 Vérifier la signature SAML** puis à **Checklist de validation minimale (dev-first)**.
En cas d'échec sur un scénario, corrigez la section concernée (voir tableau ci-dessous), puis rejouez le scénario avant de passer au suivant.

| Symptôme observé | Étape à vérifier d'abord |
| --- | --- |
| Signature invalide ou assertion refusée | 4.3 Vérifier la signature SAML |
| Response non reçue au callback ACS | 4.5 Binding puis 4.6 Callback ACS |
| Attributs manquants dans la session applicative | 4.6 Callback ACS, puis **Attributs (Legacy → IdP)** |
| Login OK mais logout incomplet | 4.7 Déconnexion (SLO vs locale) |
| Erreurs intermittentes selon environnement | 4.1 Métadonnées/certificats puis 4.3 Signature |

#### 4.8.2 Definition of Done (DoD) — validation minimale avant livraison

- Login OK validé sur le parcours nominal.
- Login KO correctement rejeté (signature/certificat/issuer/binding incohérent).
- Mapping d'attributs validé (NameID + attributs attendus).
- Déconnexion validée (SLO si activé, sinon locale).
- Logs exploitables en cas d'échec, sans fuite de données sensibles.
- PV de recette fonctionnelle hors production (dev / recette) validé avec le CAM Eagles.
- PV de recette fonctionnelle pré-production validé avec le CAM Eagles.
- PV de recette fonctionnelle production validé avec le CAM Eagles.

**Sortie attendue :** flux SAML opérationnel et diagnostiquable de bout en bout (login, erreurs, logout).

## 6. Pièges courants

- **Compte non habilité** : tester avec un compte non habilité et conclure à un problème SAML alors que c'est un problème de droits applicatifs.
- **Cache navigateur / session legacy** : après la bascule, un cookie Gardian résiduel peut fausser le test. Forcer une suppression des cookies du domaine pour reproduire un parcours SAML propre.
- **Attribut absent** : l'attribut n'apparaît pas dans l'Assertion parce qu'il n'a pas été demandé dans la **fiche de renseignement** ou n'est pas mappé côté Entra ID. Vérifier le tableau **§ 5. Attributs (Legacy → IdP)** et la demande IAM avant de modifier le code.

  Pour lister les attributs effectivement reçus dans l'Assertion (hors production uniquement, à supprimer après debug) :

  ```php
  // PHP (onelogin/php-saml)
  $auth->processResponse();
  error_log('NameID : ' . $auth->getNameId());
  error_log(print_r($auth->getAttributes(), true));
  ```

  ```python
  # Python (python3-saml)
  auth.process_response()
  print('NameID :', auth.get_nameid())
  print(auth.get_attributes())
  ```

  ```typescript
  // Node.js (passport-saml) — dans la callback Strategy
  (req, profile, done) => {
    console.log(profile); // nameID + tous les attributs reçus
    return done(null, profile);
  }
  ```
- **Métadonnées** : `EntityID` et `ACS` doivent être cohérents entre SP et IdP ; attention aux environnements (hors production vs pré-production vs production).
- **Certificats** : expiration, bon certificat (signature vs chiffrement) selon la config IdP.
- **Binding** : HTTP-POST vs HTTP-Redirect pour Request/Response ; adapter la bibliothèque et l'IdP.

## 7. Exemples de code

En gestion privée, les attributs proviennent de l'**Assertion SAML** (NameID + attributs) après validation au callback ACS — pas des variables `OIDC_CLAIM_*` (réservées à l'OIDC en gestion managée, guide **1.1**). Voir **§ 4.6** et **§ 5. Attributs (Legacy → IdP)**.

### PHP (Symfony avec onelogin/php-saml)

```php
// Configuration SP : IdP entity ID, SSO URL, x509 cert, etc.
// Après réception du POST ACS :
$auth = new OneLogin\Saml2\Auth($settings);
$auth->processResponse();
$attributes = $auth->getAttributes();
$role = $attributes['role'][0] ?? null;
```

### TypeScript (Node, passport-saml)

```typescript
// Strategy config : entryPoint, cert, callbackUrl, etc.
// Dans la callback après validation :
(req: Request, res: Response) => {
  const profile = (req as any).user;
  const attributes = profile.attributes;
  const role = attributes?.role?.[0];
}
```
