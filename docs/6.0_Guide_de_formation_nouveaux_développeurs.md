# 6. Guide de formation — Nouveaux développeurs

Point d'entrée pédagogique pour tout développeur rejoignant l'équipe de raccordement SSO.
Structuré en 7 modules progressifs, du contexte général jusqu'à la mise en pratique sur dépôt réel.

**Durée estimée totale :** ~2 jours (adaptable selon le profil et le projet d'affectation).

**Prérequis :** accès à l'espace Confluence du projet, compte GitLab opérationnel, accès au ticket Jira de l'application concernée.

---

| Module | Titre | Durée | Documents à lire |
| --- | --- | --- | --- |
| **1** | Contexte & concepts | ~3h | **0. Migration SSO Eagles — Vue d'ensemble** |
| **2** | OIDC — Gestion managée | ~2h | **1.1** Guide OIDC managée + **3.1** Correspondance claims |
| **3** | OIDC — Gestion privée | ~4h | **1.2** Guide OIDC privée + **3.1** Correspondance claims + **3.2** Guide visuel PKCE |

| **7** | Mode opératoire IA | variable | Dépôt d'exercice fourni par le formateur |

**Ordre recommandé :** M1 → M2 ou M3 ou M4 (selon votre premier projet) → M5 → M6 → M7.
M7 se fait sur un dépôt réel ; commencez-le uniquement après avoir lu le guide correspondant à votre projet.
Les modules 2, 3 et 4 peuvent être abordés dans n'importe quel ordre après M1 ; commencez par le protocole du projet sur lequel vous intervenez.

## Module 1 — Contexte & concepts (~3h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- situer la migration dans son contexte (pourquoi, qui, quels environnements) ;
- distinguer authentification et autorisation ;
- décoder la structure d'un JWT ;
- définir les concepts clés OIDC et SAML ;
- choisir le bon guide pour votre premier projet.

### Exercice

Décoder manuellement un JWT de test sur [https://jwt.io](https://jwt.io) et identifier : `iss`, `aud`, `sub`, `exp`, `email`.
Quel claim sert d'identifiant stable pour corréler un utilisateur en base de données ?

---

## Module 2 — OIDC Gestion managée — Guide 1.1 (~2h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- expliquer ce que fait le module Apache `mod_auth_openidc` à la place de l'application ;
- lire un claim dans les variables d'environnement (`OIDC_CLAIM_*` vs `REDIRECT_OIDC_CLAIM_*`) ;
- adapter le code dans les langages courants (PHP, Python, TypeScript) ;
- dérouler les phases A→F du tableau de suivi.

---

## Module 3 — OIDC Gestion privée — Guide 1.2 (~4h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- choisir entre flux avec et sans PKCE selon le type d'application ;
- implémenter les étapes du flux Authorization Code (§ 4.1 à § 4.8) ;
- valider un ID Token (signature, issuer, audience, nonce, expiration) ;
- identifier et corriger les pièges courants (`redirect_uri`, state/CSRF, secret exposé, scopes manquants).

---

## Module 4 — SAML Gestion privée — Guide 1.3 (~4h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- distinguer les deux chantiers SAML (contrat SP/IdP vs mapping applicatif) et ne pas les mélanger ;
- configurer une bibliothèque SAML avec les métadonnées IdP ;
- implémenter le callback ACS (réception Response, validation signature, extraction NameID/attributs, session) ;
- choisir et tester la stratégie de déconnexion (SLO ou locale).

---

## Module 5 — Processus & communication (~1h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- utiliser le bon template de mail à chaque étape clé ;
- tracer correctement dans Jira (mails, MR, dates de déploiement) ;
- identifier clairement ce qui est dans votre périmètre.

### Les templates de mail

| Template | Quand l'utiliser |
| --- | --- |
| **4.1 Prise en charge technique (gestion managée)** | Étape 13 du guide **1.1** : vous prenez en charge les modifications de code. |
| **4.2 Fin d'intervention technique (guide 1.1)** | Après la MR du guide **1.1**. |
| **4.3 Prise en charge technique (gestion privée)** | Étapes 10, 19, 27 du guide **1.2** / étapes 10, 22, 32 du guide **1.3**. |
| **4.4 Information utilisateurs** | Avant toute mise en production (guides **1.1**, **1.2**, **1.3**). |
| **4.5 Fin d'intervention technique (guides 1.2 / 1.3)** | Après la MR des guides **1.2** ou **1.3**. |

### Le PV de recette — votre rôle exact

- Vous **accompagnez** la recette SSO (connexion, déconnexion, affichage des claims).
- Vous **ne signez pas** le PV : c'est la responsabilité exclusive de l'équipe applicative.
- Le PV est **validé avec le CAM Eagles**.

### Périmètre de mission

> [!NOTE]
> **Dans votre scope** : transmission de la fiche de renseignement à l'IAM, injection des credentials reçus (client_id, client_secret, endpoints...) dans les variables d'environnement, adaptation du code applicatif, suivi des bascules, recette SSO.
>
> **Hors scope par défaut** : déploiement applicatif, provisionnement d'infrastructure.
>
> **Exception** : si l'équipe applicative est en défaillance DevOps, vous pouvez intervenir sur le déploiement (voir document **5. Guides de déploiement**).

## Module 6 — Déploiement (~1h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- identifier les deux modes de déploiement (manuel vs pipeline) ;
- savoir quand il vous revient d'intervenir sur le déploiement ;
- réaliser un déploiement manuel pas à pas (MyConsole Cloud, Console Web AWS, Docker Compose).

## Module 7 — Mode opératoire : migration avec assistance IA

### Objectifs

À l'issue de ce module, vous êtes capable de :

- conduire une migration SSO de bout en bout sur un dépôt réel avec assistance IA ;
- produire un historique Git propre et une MR reviewable par un pair ;
- identifier des améliorations à remonter sur le dépôt **init-dev**.

**Prérequis :** dépôt applicatif d'exercice fourni par le formateur, dépôt **init-dev** cloné (agents, instructions Copilot/Cursor), guide de migration choisi (1.1, 1.2 ou 1.3).

---

### Étape 1 — Audit IA du code existant

**Objectif :** cartographier le périmètre avant de toucher au code.

1. Ouvrir le projet dans l'IDE avec les instructions IA de **init-dev** actives.
2. Lancer l'agent d'audit en lui donnant ce prompt (ou l'équivalent présent dans init-dev) :

   > Audite ce projet et liste : toutes les références à Gardian SSO / authentification legacy, les points d'entrée d'authentification (login, logout, session, middleware), les dépendances liées à l'auth.

3. Documenter les résultats dans le ticket Jira **avant** de commencer le code.

> [!NOTE]
> L'audit IA accélère la découverte — il ne la remplace pas. Relisez les résultats critiquement et croisez avec le guide.

---

### Étape 2 — Plan d'exécution (mode Plan)

**Objectif :** définir le travail avant d'écrire une ligne de code.

1. **Passer en mode Plan** dans l'IDE (Cursor : `Ctrl+Shift+P` → Plan Mode).
2. Fournir le contexte complet :

   > Contexte : migration SSO de [NOM_APP] vers Entra ID, guide [1.x] — gestion [managée/privée].
   > Résultats d'audit : [coller les résultats de l'étape 1].
   > Contraintes : respecter les règles du dépôt init-dev (nommage, PSR-12, tests...).
   > Découper en petites étapes validables une par une ("human in the loop").

3. **Valider le plan avec un senior** avant de passer à l'étape 3 — un plan mal découpé génère des diff illisibles.

> [!WARNING]
> Ne pas lancer l'exécution sans plan validé. Chaque étape doit être autonome : si elle échoue, le rollback ne casse pas les autres.

---

### Étape 3 — Exécution pas à pas

**Principe :** une étape du plan = une unité de travail = une validation humaine.

Pour chaque étape :

1. Repasser en **mode Agent** (exécution).
2. Exécuter **une seule étape** — ne pas laisser l'IA enchaîner sans validation.
3. **Relire le diff** avant d'accepter les changements.
4. Tester manuellement : login OK, claims affichés, aucune régression.
5. Si un doute : demander à l'IA *"est-ce conforme au plan ?"* avant de continuer.
6. Commiter (étape 4) puis passer à l'étape suivante.

---

### Étape 4 — Commits réguliers

**Règle :** un commit par unité logique, pas par fichier ni par heure.

Format **Conventional Commits** (obligatoire) :

```
feat(auth): replace Gardian session check by OIDC claim reader
fix(auth): handle missing OIDC_CLAIM_email with fallback
chore(deps): add onelogin/php-saml ^4.0
```

**À la fin**, squasher les commits WIP/fix intermédiaires avant la MR :

```bash
git rebase -i origin/main
# "squash" ou "fixup" sur les commits à fusionner
# Conserver un message propre par étape logique distincte
```

> [!NOTE]
> Ne pas squasher des étapes logiquement distinctes (audit initial, adaptation code, config env, déploiement sont des commits séparés à garder).

---

### Étape 5 — Merge Request

1. Pousser la branche : `git push -u origin feat/sso-[protocol]-[nom-app]`
2. Ouvrir la MR en **Draft** dès le début — le reviewer peut suivre l'avancement en temps réel.
3. Remplir la description :
   - **Contexte** : application, guide suivi, protocole
   - **Ce qui change** : fichiers clés, claims / attributs migrés
   - **Comment tester** : URL de login, claims attendus, scénario KO
   - **Lien Jira**
4. Attendre que la **CI passe** avant de demander une review (évite les allers-retours stériles).
5. Passer Draft → **Ready** quand les tests sont verts.
6. Assigner **au moins un senior** de l'équipe de raccordement — ne pas merger soi-même sauf accord explicite.

---

### Tricks & pièges à ne pas oublier

| Sujet | À faire |
| --- | --- |
| **Nommage de branche** | `feat/sso-oidc-[app]` ou `feat/sso-saml-[app]` |
| **Secrets dans le code** | Vérifier `git diff` avant chaque commit — `client_secret`, tokens, API keys ne doivent jamais apparaître |
| **`.env` à ne pas committer** | Toujours avoir un `.env.example` à jour ; le `.env` réel doit être dans `.gitignore` |
| **Test en navigation privée** | Les cookies Gardian résiduels faussent les tests — toujours tester dans un contexte vierge |
| **Commentaires inline MR** | Pour les choix non évidents (ex. "pourquoi ce claim ?"), expliquer dans la MR plutôt que dans le code |
| **Conflits avec main** | Rebaser régulièrement : `git fetch && git rebase origin/main` — ne pas laisser diverger trop longtemps |
| **Linting avant commit** | Lancer le linter (PHP CS Fixer, ESLint...) avant chaque commit pour éviter les retours de review superficiels |
| **CI rouge = ne pas merger** | Même si "c'est juste une alerte" — corriger d'abord |

---

### Contribuer à l'amélioration de init-dev

Pendant cet exercice, notez tout ce qui vous a bloqué ou ralenti et qui aurait pu être résolu par une meilleure configuration de **init-dev**.

| Observation terrain | Amélioration possible dans init-dev |
| --- | --- |
| L'IA a proposé du code incompatible avec la version PHP du projet | Ajouter la version cible dans les instructions Copilot/Cursor |
| L'IA n'a pas respecté les conventions de nommage | Enrichir `.cursorrules` / instructions agents |
| L'agent d'audit a manqué des points d'entrée d'auth | Affiner le prompt d'audit dans les agents init-dev |
| Un piège SSO connu (ex. `redirect_uri`) s'est répété | Ajouter une règle de guard dans les instructions IA |
| Une étape du guide manque de clarté pour l'IA | Remonter sur la doc SSO (issue ou MR) |

Remonter ces observations en fin d'exercice : **commentaire Jira** ou **MR sur init-dev** avec le label `amélioration/formation`.
