# 6. Guide de formation — Nouveaux développeurs

Ce document est le **point d'entrée pédagogique** pour tout développeur rejoignant l'équipe de raccordement SSO.
Il structure la prise en main de la documentation en 7 modules progressifs, du contexte général jusqu'à la mise en pratique sur un cas réel.

**Durée estimée totale :** environ 2 jours (adaptable selon le profil et le projet d'affectation).

**Prérequis** : accès à l'espace Confluence du projet, compte GitLab opérationnel, accès au ticket Jira de l'application concernée.

## Module 0 — Contexte & onboarding (~2h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- expliquer pourquoi la migration SSO est lancée et ce qu'elle remplace ;
- nommer les acteurs et décrire leur rôle ;
- identifier les 3 environnements de migration ;
- choisir le bon guide détaillé en croisant protocole et mode de gestion.

### Contenu

**Pourquoi cette migration ?**

L'authentification historique repose sur **Gardian SSO** (IdP legacy du SI). La migration consiste à basculer l'ensemble des applications vers **Microsoft Entra ID** (anciennement Azure AD), le nouvel IdP cible. Chaque application migrate séparément, selon un parcours standardisé en phases.

**Les acteurs**

| Acteur | Rôle |
| --- | --- |
| **CAM Eagles** | Chef de projet migration : suit le planning, transmet la fiche de renseignement, cadence les jalons, cosigne les PV de recette. |
| **Équipe IAM** | Configure Entra ID (côté IdP) : enregistre l'application, définit les claims/attributs émis, transmet les métadonnées IdP ou credentials (Client ID / Client Secret). |
| **Équipe Gestion managée** | Pour les apps Cloud Place : configure le module Apache OIDC à la place de l'application (gestion managée). |
| **Équipe de raccordement** | Vous. Adapte le code, réalise la recette SSO, accompagne ou remplace l'équipe applicative. |
| **Équipe applicative** | Propriétaire de l'application. Valide fonctionnellement et signe le PV de recette. |

**Les 3 environnements**

| Environnement | Rôle | Phases du guide |
| --- | --- | --- |
| **Hors production** | Dev / Recette — premier environnement raccordé, souvent déploiement manuel | A → D |
| **Pré-production** | Staging — souvent pipeline GitLab, proche de la production | E |
| **Production** | Environnement live | F |

**Choisir votre guide**

Croisez 2 critères uniquement :

| Protocole | Mode de gestion | Guide |
| --- | --- | --- |
| OIDC | Gestion managée (Apache, Cloud Place) | **1.1 Guide OIDC Gestion managée** |
| OIDC | Gestion privée (code applicatif gère le flux) | **1.2 Guide OIDC Gestion privée** |
| SAML | Gestion privée (code applicatif gère le flux) | **1.3 Guide SAML Gestion privée** |

En cas de doute sur le protocole ou le mode, consultez le tableau de routage du **1. Guides de migration SSO**.

### Lecture obligatoire

- **0. Migration SSO – Eagles** — intégralité (focus sur : vue d'ensemble, périmètre de mission, les 3 environnements, prérequis, étapes communes, glossaire).

### Points d'attention

- Votre rôle **n'inclut pas** par défaut le déploiement applicatif. Vous n'intervenez sur ce point qu'en cas de défaillance DevOps côté applicatif (exception explicitement décrite dans chaque guide).
- Vous **n'êtes pas** le signataire du PV de recette : vous accompagnez la validation, la décision finale appartient à l'équipe applicative et au CAM Eagles.

## Module 1 — Concepts fondamentaux (~2h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- distinguer authentification et autorisation ;
- décoder la structure d'un JWT (header, payload, signature) ;
- définir les concepts clés OIDC (ID Token, Access Token, claim, scope, PKCE) ;
- définir les concepts clés SAML (Assertion, SP, IdP, ACS, SLO, NameID).

### Contenu

**Authentification vs autorisation**

- **Authentification** : vérifier l'identité de l'utilisateur ("qui es-tu ?").
- **Autorisation** : déterminer ce que l'utilisateur a le droit de faire ("qu'as-tu le droit de faire ?").

Le SSO gère l'authentification. L'autorisation reste dans le code applicatif (rôles, claims).

**Structure d'un JWT**

Un JWT (JSON Web Token) est composé de 3 parties encodées en Base64url, séparées par des points :

```text
HEADER.PAYLOAD.SIGNATURE
```

- **Header** : algorithme de signature (ex. `RS256`) et identifiant de clé (`kid`).
- **Payload** : les **claims** — informations sur l'utilisateur et le jeton (`sub`, `email`, `exp`, `iss`, `aud`, etc.).
- **Signature** : permet de vérifier que le jeton n'a pas été altéré (clé publique de l'IdP via JWKS).

**Concepts OIDC essentiels**

| Terme | À retenir |
| --- | --- |
| **ID Token** | JWT contenant l'identité de l'utilisateur — c'est lui qu'on valide et dont on lit les claims. |
| **Access Token** | Jeton OAuth 2.0 pour appeler des APIs protégées. Ne pas confondre avec l'ID Token. |
| **Claim** | Champ du payload JWT : `sub` (identifiant), `email`, `name`, `roles`, `exp` (expiration)... |
| **Scope** | Portée demandée : `openid` (obligatoire OIDC), `profile`, `email`, `offline_access` (refresh token). |
| **PKCE** | Renforcement sécurité pour apps sans backend sécurisé (SPA, mobile). `code_verifier` + `code_challenge`. |
| **Discovery** | Document `/.well-known/openid-configuration` : fournit tous les endpoints de l'IdP. Ne pas coder les URLs en dur. |

**Concepts SAML essentiels**

| Terme | À retenir |
| --- | --- |
| **SP** | Service Provider : votre application, qui consomme l'authentification. |
| **IdP** | Identity Provider : Entra ID, qui fournit l'Assertion SAML. |
| **Assertion** | Bloc XML signé contenant l'identité de l'utilisateur (NameID + attributs). |
| **ACS** | Assertion Consumer Service : endpoint de votre app qui reçoit la Response SAML (en POST). |
| **NameID** | Identifiant de l'utilisateur dans l'Assertion. Format défini dans la fiche de renseignement. |
| **SLO** | Single Logout : déconnexion synchronisée IdP ↔ SP. Optionnel mais recommandé. |
| **Binding** | Méthode de transport SAML : `HTTP-Redirect` (AuthnRequest) ou `HTTP-POST` (Response). |

### Lecture

- **0. Migration SSO – Eagles**, sections 3.1 (OIDC/OAuth), 3.2 (SAML), 3.3 (concepts transverses), 3.4 (acteurs & plateformes).

## Module 2 — OIDC Gestion managée — Guide 1.1 (~2h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- expliquer ce que fait le module Apache `mod_auth_openidc` à la place de l'application ;
- lire un claim dans les variables d'environnement (préfixe `OIDC_CLAIM_...` vs `REDIRECT_OIDC_CLAIM_...`) ;
- adapter le code dans les langages courants (PHP, Python, TypeScript) ;
- dérouler les phases A→F du tableau de suivi du guide **1.1**.

### Contenu

**Le principe de la gestion managée**

En gestion managée, **votre application ne code pas le flux OIDC**. Le module Apache (`mod_auth_openidc`) :

- redirige l'utilisateur vers Entra ID ;
- échange le code contre les tokens ;
- valide l'ID Token ;
- **injecte les claims dans les variables d'environnement de la requête HTTP**.

Votre code se contente de **lire** ces variables.

**Lire les claims**

```text
Préfixe standard     : OIDC_CLAIM_[NOM_DU_CLAIM]
Préfixe après redir. : REDIRECT_OIDC_CLAIM_[NOM_DU_CLAIM]
```

Si un claim est vide, testez les deux préfixes. La casse compte (`OIDC_CLAIM_email` ≠ `OIDC_CLAIM_Email`).

**Exemples de lecture (extraits)**

```php
// Symfony
$email = $request->server->get('OIDC_CLAIM_email');
$role  = $request->server->get('OIDC_CLAIM_role');
// PHP natif
$email = $_SERVER['OIDC_CLAIM_email'] ?? null;
```

```python
# Flask
email = request.environ.get('OIDC_CLAIM_email')
role  = request.environ.get('OIDC_CLAIM_role')
```

```javascript
// Node.js / Express (Apache transmet souvent les claims en en-têtes HTTP)
const email = req.headers['oidc-claim-email'];
const role  = req.headers['oidc-claim-role'];
```

**Parcours A→F (rappel)**

| Phase | Contenu |
| --- | --- |
| Phase A | Préparer : accès, habilitations, Client ID / Client Secret |
| Phase B | Raccorder SSO hors production (équipe Gestion managée) |
| Phase C | Adapter le code (remplacer les claims legacy) |
| Phase D | Basculer hors production : planifier + déployer + recette |
| Phase E | Raccorder SSO et basculer pré-production |
| Phase F | Raccorder SSO et basculer production |

### Pièges à retenir

- Claim absent = soit non demandé dans la fiche de renseignement, soit non émis par Entra ID → vérifier avant de modifier le code.
- Cookie Gardian résiduel : forcer la suppression des cookies après bascule pour tester proprement.
- En gestion managée, vous n'implémentez **pas** de bibliothèque OIDC.

- **1.1 Guide migration OIDC – Gestion managée** — intégralité.
- **3.1 Correspondance des claims OIDC** — table de correspondance Legacy ↔ Entra ID.

## Module 3 — OIDC Gestion privée — Guide 1.2 (~4h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- choisir entre flux avec et sans PKCE selon le type d'application ;
- implémenter les 7 étapes du flux Authorization Code (JWKS → authorize → callback → token → validation → refresh → UserInfo) ;
- valider un ID Token (signature, issuer, audience, nonce, expiration) ;
- identifier et corriger les pièges courants (`redirect_uri`, state/CSRF, secret exposé, scopes manquants).

### Contenu

**Décision PKCE — règle simple**

| Type d'application | Décision |
| --- | --- |
| SPA, app mobile (pas de backend sécurisé) | Utiliser **PKCE** (sans `client_secret`). |
| Application avec backend (Symfony, Spring, Node, Python...) | `client_secret_basic` ; PKCE non obligatoire par défaut, mais s'ajoute automatiquement si Entra ID impose **"Require PKCE"** ou si votre bibliothèque OIDC le génère (voir **3.2**, section 5). |

**Flux Authorization Code — les 7 étapes**

```text
4.1  Récupérer JWKS via Discovery (.well-known/openid-configuration)
4.2  Rediriger vers /authorize (client_id, redirect_uri, scope, state, nonce)
4.3  Recevoir le code au callback + vérifier state (anti-CSRF)
4.4  Échanger le code contre les tokens (POST /token)
4.5  Valider l'ID Token (signature JWKS, iss, aud, nonce, exp)
4.6  Rafraîchir l'Access Token avec refresh_token (si offline_access)
4.7  Appeler UserInfo si claims manquants dans l'ID Token
```

**Contrôles minimaux à l'étape 4.5**

| Contrôle | Vérification |
| --- | --- |
| Signature | Clé publique correspondant au `kid` ; algorithme RS256. |
| Issuer (`iss`) | Correspond au tenant attendu. |
| Audience (`aud`) | Correspond au `client_id`. |
| Expiration (`exp`) | Non expiré. |
| Nonce | Identique à celui envoyé en 4.2 (anti-rejeu). |

**Pièges courants à mémoriser**

- `redirect_uri` : doit être **exactement** identique (protocole, domaine, port, chemin) entre authorize et token.
- `state` : générer une valeur unique **par requête** et la vérifier au callback avant d'échanger le code.
- `client_secret` : côté backend **uniquement**, jamais exposé dans le front ni committé.
- Scopes : `openid` est obligatoire. Les claims personnalisés peuvent nécessiter des scopes supplémentaires.

### Checklists à connaître

- **4.8.1 Checklist rapide** : `state`, `iss`/`aud`/`ver`, `redirect_uri`, gestion d'erreur.
- **4.8.2 DoD** : login OK/KO, claims validés, déconnexion locale, logs sans fuite de données, PV de recette validés avec le CAM Eagles.

### Lecture

- **1.2 Guide migration OIDC – Gestion privée** — intégralité (particulièrement sections 3, 4.1 à 4.9, 5).
- **3.2 Comprendre le flux OIDC et PKCE — Guide visuel** — schémas et analogies pour bien visualiser le flux web app vs SPA.

## Module 4 — SAML Gestion privée — Guide 1.3 (~4h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- distinguer les deux chantiers SAML (contrat SP/IdP vs mapping applicatif) et ne pas les mélanger ;
- configurer une bibliothèque SAML avec les métadonnées IdP ;
- implémenter le callback ACS (réception Response, validation signature, extraction NameID/attributs, création de session) ;
- choisir et tester la stratégie de déconnexion (SLO ou locale).

### Contenu

**Les deux chantiers — à ne jamais mélanger**

| Chantier | Ce que c'est | Étapes du suivi |
| --- | --- | --- |
| **Contrat SP/IdP** | URL publique, ACS, EntityID, SLO, bindings, certificats — ce que l'IAM configure côté Entra ID | Étapes 7, 9, 11, 12 |
| **Mapping applicatif** | Lire NameID + attributs dans l'Assertion et les mapper vers le modèle applicatif | Étapes 8, 15 |

Si le contrat SP/IdP est faux, le SAML casse **avant** que votre mapping ne serve à quoi que ce soit. Validez-le en premier.

**Flux SP-initiated (recommandé)**

```text
1. Utilisateur accède à l'app (SP)
2. SP génère AuthnRequest → HTTP-Redirect vers IdP
3. IdP authentifie l'utilisateur
4. IdP envoie Response SAML signée → HTTP-POST vers ACS du SP
5. SP valide la signature, extrait NameID/attributs, crée la session
```

**Validation de signature — règle fondamentale**

- **Ne jamais désactiver** la vérification de signature, même en développement.
- Configurer la bibliothèque SAML avec le certificat x509 de l'IdP (issu des métadonnées reçues de l'IAM).
- Vérifier au bon niveau : Response, Assertion ou les deux — selon ce qui est configuré côté Entra ID.

**Checklist de validation minimale (dev-first)**

- Signature SAML : présente et valide.
- Issuer : correspond à l'IdP attendu.
- Audience : correspond à l'EntityID du SP.
- Fenêtre de validité : `NotBefore` / `NotOnOrAfter` cohérents.
- Correlation : `InResponseTo` correspond à l'AuthnRequest (en SP-initiated).

**Déconnexion : SLO ou locale**

| Stratégie | Quand l'utiliser |
| --- | --- |
| **SLO SAML** | Si Entra ID est configuré avec une `LogoutURL` et que la synchronisation inter-apps est nécessaire. |
| **Déconnexion locale** | Fallback simple : détruire la session applicative + redirection vers l'URL de déconnexion Entra ID. |

### Pièges à retenir

- Confondre le contrat SP/IdP avec le mapping applicatif est la source d'erreur n°1 sur les projets SAML.
- L'EntityID et l'ACS doivent être cohérents entre SP et IdP dans **chaque** environnement.
- Les certificats expirent : prévoir une procédure de rotation.

### Lecture

- **1.3 Guide migration SAML – Gestion privée** — intégralité (particulièrement sections 3, 4.1 à 4.8, 5, 6).
- **3.3 Comprendre le flux SAML — Guide visuel** — schémas et analogies pour bien visualiser SP-initiated vs IdP-initiated et le rôle de la signature.
- **3.4 Checklist de demande IAM – Raccordement SAML** — informations à transmettre à l'IAM pour chaque demande de raccordement (hors production, pré-production, production).

- Vous **accompagnez** la recette SSO (connexion, déconnexion, affichage des claims dans les pages concernées).

- Le PV est **validé avec le CAM Eagles** (séance de revue commune).

### Traçabilité Jira — ce qui doit y être

- Lien vers la Merge Request GitLab.
- Dates de déploiement par environnement.

- Tout blocage ou écart constaté.

### Périmètre de mission — aide-mémoire

>

>
> **Exception** : si l'équipe applicative est en défaillance DevOps, vous pouvez intervenir sur le déploiement (voir **5. Guides de déploiement**).

## Module 6 — Déploiement (~1h)

### Objectifs

À l'issue de ce module, vous êtes capable de :

- identifier les deux modes de déploiement (manuel vs pipeline) ;
- savoir quand il vous revient d'intervenir sur le déploiement ;
- réaliser un déploiement manuel pas à pas (MyConsole Cloud, Console Web AWS, Docker Compose).

### Les deux modes

| Mode | Quand | Guide |
| --- | --- | --- |
| **Manuel** | Déploiement à la main via MyConsole Cloud et Console Web AWS | **5.1 Déploiement manuel** |
| **Automatique** | Pipeline GitLab (hors production, pré-prod, prod) | **5.2 (à rédiger)** |

### La clause d'exception DevOps

Dans chaque étape de déploiement des guides 1.1 à 1.3, vous trouverez :

> "En cas de défaillance en ressource technique DevOps côté applicatif, réaliser le déploiement ; sinon, le demander à l'équipe applicative."

Cela signifie : par défaut, c'est l'équipe applicative qui déploie. Vous n'intervenez que si elle est en capacité insuffisante.

### Séquence de déploiement manuel (résumé)

1. Vérifier l'infrastructure (schéma d'architecture, instances EC2).
2. Sauvegarder le répertoire courant (`cp -R /opt/app /opt/app.bak`).
3. Préparer les sources : `git fetch`, `git checkout [branche]`, `git pull`.
4. Mettre à jour les variables d'environnement (`.env`) : Client ID, Client Secret, OIDC/SAML endpoints.
5. Vérifier l'image Docker et reconstruire si nécessaire.
6. Redémarrer les conteneurs : `docker compose up -d [service]`.
7. Vérifier les logs : `docker compose logs -f [service]`.
8. Tester la connexion SSO (login OK, claims ou attributs affichés).
9. En cas d'échec : rollback — `rm -rf /opt/app`, puis `mv /opt/app.bak /opt/app`.

### Exercice 3 — Diagnostiquer à partir d'un log (~1h)

**Log fictif :**

```text
[ERROR] Token validation failed: invalid_grant
[ERROR] redirect_uri_mismatch: https://app.example.com/callback vs https://app.example.com/callback/

```

**Questions :**

1. Que signifie `invalid_grant` ? Quelle section du guide 1.2 consulter ?

### Quiz de clôture (~30 min)

**Vrai / Faux — répondre sans consulter la documentation :**

1. Un ID Token et un Access Token sont la même chose. *(Faux)*
2. En gestion managée, l'application implémente le flux OIDC dans son code. *(Faux)*
3. Le `redirect_uri` peut légèrement varier entre authorize et token. *(Faux)*
4. Le CAM Eagles signe le PV de recette à la place de l'équipe applicative. *(Faux)*
5. Le binding HTTP-POST est utilisé pour envoyer la Response SAML vers l'ACS. *(Vrai)*
6. En gestion privée OIDC, les claims se lisent dans `OIDC_CLAIM_...`. *(Faux — c'est la gestion managée)*
7. PKCE est obligatoire pour les apps avec backend sécurisé. *(Faux par défaut — mais peut le devenir selon la configuration Entra ID ou la bibliothèque OIDC utilisée, voir **3.2** section 5)*
8. La vérification de signature SAML peut être désactivée en développement pour tester plus vite. *(Faux)*

- Identifier votre premier projet réel et ouvrir le ticket Jira associé.
