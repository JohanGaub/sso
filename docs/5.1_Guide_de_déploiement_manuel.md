# 5.1 Déploiement manuel

Ce guide décrit le **déploiement manuel** d'une application conteneurisée (Docker Compose) sur instances EC2 via MyConsole Cloud et Console Web AWS.

Il s'applique **quel que soit l'environnement** dès lors que le déploiement se fait à la main (pas de pipeline GitLab).

**Prérequis** : accès MyConsole Cloud, accès Console Web AWS, et — si applicable — compte utilisateur applicatif pour vérifier l'affichage des claims ou attributs SSO.

**Adapter** les commandes, noms de services, chemins et filtres d'environnement à votre projet.

Le déploiement **automatique** (pipeline GitLab) sera documenté dans **5.2 Déploiement automatique** **(à rédiger)**.

**Index** : **5. Guides de déploiement**.

## 1. Préparation de l'infrastructure

### 1.1 Consultation du schéma d'architecture

Accéder à :

[https://archifactory.enedis.fr](https://archifactory.enedis.fr)

- Rechercher l'application à l'aide de son identifiant INS.
- Cliquer sur **Architecture**.
- Cliquer sur **Schéma d'architecture**.

Identifier :

- les composants frontend ;
- les composants backend ;
- les bases de données ;
- les CDN ;
- les load balancers ;
- les firewalls ;
- le mode d'hébergement :
  - EC2 ;
  - VM ;
  - conteneur ;
  - partition cloud ;
  - hébergement mutualisé ;
  - hébergement dédié.

### 1.2 Identification des instances

Accéder à :

[https://inventaire.enedis.fr](https://inventaire.enedis.fr)

Navigation :

- Applications

Puis :

Filtrer l'environnement cible :

```

RECETTE
```

- les instances frontend ;

Depuis [console.web-enedis.fr](https://console.web-enedis.fr) :

- sélectionner l'instance ;
- cliquer sur l'engrenage ;
- sélectionner **Shell web**.

Passage en administrateur :

```bash

```

Vérifier :

```bash
whoami
```

Résultat attendu :

```

```

## 4. Sauvegarde préalable

Avant toute modification :

Identifier le répertoire applicatif. Les applications sont généralement dans :

```
/opt/monapp
/srv/monapp
/home/deploy/monapp
```

Se positionner dans le répertoire parent :

```bash
cd /opt
# ou /srv, /home/deploy — adapter selon le projet
```

Vérifier l'espace disque disponible :

```bash
ncdu /
```

Créer une sauvegarde horodatée :

```bash
cp -R monapp monapp_$(date +%Y%m%d)
# Résultat ex. : monapp_20250716
```

> [!WARNING]
> Toujours conserver une copie de l'application avant déploiement afin de faciliter un éventuel rollback.

## 5. Mise à jour du code (branche de migration SSO)

Se positionner dans le répertoire applicatif :

```bash
cd /opt/monapp
# adapter selon le projet
```

Vérifier la branche courante :

```bash
git status
git branch --show-current
```

Résultat attendu : la branche de migration SSO du projet (ex. `migration-sso`).

Si besoin, basculer et mettre à jour :

```bash
git fetch
git checkout migration-sso
# adapter le nom de branche si différent
git pull
```

## 7. Configuration de l'environnement

Créer le fichier de configuration :

```bash
cp .env.example .env
```

Éditer :

```bash
vim .env
```

Variables SSO à vérifier / renseigner selon le protocole :

**OIDC :**

```env
OIDC_CLIENT_ID=<client_id_fourni_par_IAM>
OIDC_CLIENT_SECRET=<secret_fourni_par_IAM>
OIDC_DISCOVERY_URL=https://login.microsoftonline.com/<tenant_id>/v2.0/.well-known/openid-configuration
APP_BASE_URL=https://monapp.<env>.enedis.fr
# ex. : monapp.recette.enedis.fr, monapp.preprod.enedis.fr, monapp.enedis.fr
```

**SAML :**

```env
SAML_IDP_SSO_URL=<sso_url_fourni_par_IAM_dans_les_métadonnées_IdP>
SAML_SP_ENTITY_ID=https://monapp.<env>.enedis.fr
SAML_ACS_URL=https://monapp.<env>.enedis.fr/saml/acs
```

Vérifier également :

- la configuration MyConsole Cloud (si utilisée par l'application) ;
- les autres secrets et paramètres environnementaux spécifiques au projet.

## 8. Construction de l'application

Prérequis : être positionné dans le répertoire contenant le fichier Docker Compose concerné.

Construction de l'image. Le nom du service est celui déclaré dans le fichier Compose (ex. `app`, `web`, `api`, `frontend`, `backend`) :

```bash
docker compose build app
# adapter "app" au nom réel du service dans votre compose.yml
```

Installation des dépendances (exemples selon la stack) :

- **Node / pnpm** :

```bash
docker compose run --rm app pnpm install --frozen-lockfile
```

- **PHP / Composer (Symfony)** :

```bash
docker compose run --rm app composer install --no-dev --optimize-autoloader
```

Migrations ou génération d'assets (si applicable) :

```bash
# Doctrine (Symfony)
docker compose run --rm app php bin/console doctrine:migrations:migrate --no-interaction

# Prisma (Node)
docker compose run --rm app npx prisma migrate deploy
```

## 9. Démarrage des services

Démarrage standard :

```bash
docker compose up -d
```

Ou avec un fichier Compose d'environnement spécifique :

```bash
docker compose -f compose.dev.yml up -d
docker compose -f compose.recette.yml up -d
docker compose -f compose.preprod.yml up -d
docker compose -f compose.prod.yml up -d
# utiliser celui qui correspond à l'environnement cible
```

Vérifier que les services déclarés dans votre fichier Compose sont bien démarrés, par exemple :

```bash
docker ps
# Résultat attendu (noms à adapter) :
# monapp-app-1        Up 2 minutes
# monapp-db-1         Up 2 minutes
# monapp-redis-1      Up 2 minutes
```

## 10. Vérifications après déploiement

Vérifier les conteneurs actifs :

```bash
docker ps
```

Consulter les logs du service applicatif (adapter le nom : `app`, `web`, `api`...) :

```bash
docker compose logs -f app
```

Consulter les logs de la base de données (adapter le nom : `db`, `postgres`, `mysql`...) :

```bash
docker compose logs -f db
```

Contrôles à réaliser :

- application accessible ;
- authentification fonctionnelle ;
- pages principales accessibles ;
- absence d'erreurs critiques dans les logs ;
- absence de boucle de redirection ;
- accès à une page protégée nécessitant une authentification ;
- absence d'erreur 500.


### Consultation des logs base de données

```bash
docker compose logs -f db
# adapter "db" au nom réel du service (postgres, mysql...)
```

### Ressources statiques

Si l'application utilise un CDN :

- vérifier la propagation des ressources statiques ;
- invalider le cache CDN si nécessaire.

---

## 12. Critères de succès du déploiement

Le déploiement peut être considéré comme réussi lorsque :

- les conteneurs sont démarrés ;
- l'application est accessible ;
- les logs ne présentent aucune erreur bloquante ;
- l'authentification fonctionne ;
- les contrôles prévus ont été réalisés ;
- le responsable applicatif a confirmé le fonctionnement attendu.

---

## 13. Rollback

Arrêt de l'application :

```bash
docker compose down
```

Restauration de la sauvegarde créée à l'étape 4 (suffixe format AAAAMMJJ) :

```bash
rm -rf monapp
mv monapp_20250716 monapp
# adapter "monapp" et la date au nom réel de la sauvegarde
```

Redémarrage :

```bash
docker compose up -d
```

Vérifier le fonctionnement de l'application et confirmer le retour à un état nominal.
